# 更新结果的生成与保留规则

`update` 与 `test` 使用相同的解析、执行、比较和失败报告逻辑。

## 预览或应用更新前

- **dry-run 仍会执行代码。** `update` 和 `update --dry-run` 都会以你的权限构建并运行
  程序，没有沙箱或临时工作区隔离。dry-run 不修改 Markdown，但程序仍可能修改文件。
- **已通过的用例也会处理。** 所有成功执行的用例都会重新生成预期；断言已经通过时，
  预期和围栏仍可能被规范化。应审阅完整文档差异，不能只看失败用例。
- **执行错误会阻止整份文档的更新。** 构建失败、超时、目标解析失败或其他执行错误，
  都会阻止该文档的全部预期编辑和 dry-run 文档差异。其他文档仍可能更新，
  之前的更新和程序副作用不会回滚。
- **更新成功不表示断言通过。** `update --dry-run` 即使打印 `FAIL`，在操作完成且没有
  错误时仍可能以 `0` 退出。CI 应使用 `test` 判断是否通过；mooncram 自身的退出码
  与被测程序的预期 `[N]` 独立。

对于有意的行为变化，先预览、审阅，再应用并验证：

```sh
mooncram update tests/example.md --dry-run
mooncram update tests/example.md
mooncram test tests/example.md
```

将 `tests/example.md` 替换为你的输入。如果使用非默认的 `--target` 和 `--timeout-ms`，
在三条命令中保持一致。非预期变化应先修程序，再决定是否更新预期。

## 更新会修改什么

只有最终文档字节发生变化，才写入或显示试运行差异。
程序输出和退出状态不变时，再次更新保持文件不变并报告 `updated 0`。

更新会保留仍匹配对应输出的 glob／regex 原文。新增或变化的输出若没有可保留的
匹配模式，就生成精确预期；已消失输出的预期会被删除。即使用例已经通过，精确预期
仍可能被规范化，包括冗余的 `(escaped)` 写法。`(no-eol)` 根据实际输出末尾是否有换行决定。

普通输出直接写入。控制字符，以及可能被识别为命令、`#cwd` 声明、流标记、
注解或末尾退出码标记的输出，使用 JSON 字符串加 `(escaped)` 保护。
空输出不生成输出行；有意义的空输出行在必要时使用 `"" (escaped)` 保留。
显式零退出码也会省略，非零退出码统一为 `[N]`。

同一测试块的开闭围栏统一采用最短安全长度，至少三个反引号。
输出类似闭合围栏时可能加长，原有围栏过长时可能缩短；已经通过的用例也可能发生这种变化。

只修改预期文本和围栏标记。命令、块配置、正文、分隔行及编辑区间外的文本保持原样，
包括文档末尾没有换行符的情况。已有输出行尽可能保留 Markdown 容器前缀和换行风格，
新增输出沿用命令行的布局。必要时调整缩进，确保 Markdown 解析后保留实际输出中的空格。

双流保留原区段顺序、首个标记前及区段之间的空行、`(ignore)` 和仍满足的 `(empty)`。
不满足的 `(empty)` 转换为普通标记及具体输出。各流独立更新。

生成差异或写入之前，校验更新后的文档保留了用例、命令和配置，并匹配捕获到的结果。
校验失败则取消整份文档的更新。变化用例各计一次，包括纯规范化；共享围栏变化计入其中所有用例。

在试运行模式中，每个存在可用编辑的文档还会额外打印：

```text
--- <canonical-file>
+++ <canonical-file> (updated)
<document diff hunks>
```

文档差异与单个用例的失败报告都会打印。拟议差异描述可应用的文档编辑；
最后的 `test` 用于验证更新后的用例通过。
